# EnergyManager V3 preview (3.0.0b1)

V3 replaces the old weighted MILP refinement. It retains the existing forecasters,
HA REST/WebSocket ingestion, timestamped tariffs, InfluxDB telemetry and history,
legacy imports, EV/ESS command translation, phase-switch interlocks, charger fault
latching/reset limits, control health and notification suppression. No live HA,
network infrastructure, database or hardware validation is claimed.

## Architecture and contracts

- `requirements.py`: immutable requirements, structured generator provenance, generic
  jobs and storage resources. `tasks.py` retains single-departure and weekly EV policies.
- `planner.py`: the complete 15-minute forecast frame and typed plan. ESS positive power
  supplies the AC bus; EV and generic load positive power consume it; grid positive is import.
- `jobs.py`: interruptible energy demands, non-interruptible power-sequence cycles and
  generic storage with charge efficiency, reserve, withdrawals and state deadlines. These
  participate in the same AC balance as EV/ESS. The thermal-storage example uses kWh;
  a device generator must convert temperature requirements into a calibrated energy model.
  These generic extensions have tested planning contracts, not invented live integrations.
- `milp_planner.py` / `hierarchy.py`: one HiGHS model, explicit objective bounds, incumbent
  reuse, complete sparse-matrix/bounds/integrality validation plus independent EV/ESS checks.
- `decision_store.py` / `decision_records.py`: immutable inputs and atomic versioned decision
  records; complete stage plans, costs, limitations and input/schedule differences.
- `counterfactual.py` / `replay.py`: frozen-input, read-only re-solves without HA clients.
- `planner_service.py`: background optimization, latest-request coalescing, rejection and
  archival of superseded results, bounded retention of a previously valid plan, independent
  fast dispatch. Storage failure degrades diagnostics, not hardware authority.
- `hardware_authority.py`: final actuator service-call guard, including private reset and
  fallback paths. Diagnostic state publication remains allowed in shadow mode.

## Requirements and time

Mandatory cumulative AC charge is
`max(0, capacity * minimum_soc / 100 + earlier_trip_energy - initial_stored_energy) / efficiency`.
The MILP enforces the actual stored-energy departure state, separately from this diagnostic
calculation. Trips withdraw battery energy at departure; away windows prohibit charging.
A terminal target uses the configured preferred SoC and total expected trip consumption.
The default preferred-shortfall penalty is the frozen import tariff per AC-equivalent kWh.
This is a policy trade-off, not a hard target or cap: SoC can exceed the preferred target.
Every generated requirement records inputs, formula, source references, quality/status,
assumptions and preliminary maximum-power feasibility. The snapshot carries source timestamps,
held/stale flags, generator configuration, capabilities, actual forecasts and revision timestamps.
A preliminary feasibility calculation is not proof that electrical constraints are feasible.

**Migration:** an omitted single-departure `ev.minimum_soc_percent` now means no hard
minimum (0%), rather than implicitly promoting `target_soc_percent` to a mandatory departure
SoC. Configure the actual departure minimum explicitly. The minimum and terminal preference
are independent: the departure minimum may exceed the preferred terminal state. Weekly
calendar entries retain their own explicit minimum and trip-energy values.

All snapshot timestamps are timezone-aware, preserving IANA zone identity and UTC instants.
Elapsed energy calculations use UTC. Recurring ambiguous autumn times select the first
occurrence (fold 0); nonexistent spring times normalize forward through the UTC round trip.
A non-quarter-hour departure conservatively credits only complete preceding slots.
The horizon remains 672 physical quarter-hours, including DST crossings.

## Objective hierarchy and accounting

Physical constraints are never relaxed. A stage without a feasible incumbent cannot create
an adoptable plan. Every successful refinement is constrained by the accepted objective plus
the stated tolerance of all earlier stages. An incumbent at a timeout is explicitly reported;
`Optimal` is the solver status within its recorded gap tolerance, not proof of an exact optimum.

| Priority | Objective | Default allowed degradation for later stages |
|---|---|---|
| Economics | import − export + incremental capacity cost + soft shortfall − usable terminal ESS credit | EUR 0.01 |
| Robustness | imported kWh weighted by `2^(-elapsed_days/3)` | 0.05 weighted kWh |
| Operating quality | actual starts + three-phase activation transitions + interruption of a currently active first slot | 0 events |
| Stability | absolute EV and grid changes over the previous accepted plan's first four overlapping hours | 0.01 kWh |
| Deterministic selection | fixed chronological EV/ESS charge ordering, fixed seed and one solver thread | final stage |

Robustness is a transparent timing heuristic, not a calibrated probability model. It only
operates inside the economic bound, so deadlines, capacity costs and valuable early purchases
remain possible. It does not forbid early grid imports or unconditionally consume PV/ESS.
Operating-quality events have equal unit cost within their own stage; starts, phase activation
transitions and active-session continuity are distinct model terms. No monetary savings are
attributed to those preferences. Later stages may remain unproven under the solve budget.
Fixed-seed selection makes completed solves repeatable; time-limited incumbents can vary.

The monthly baseline is sunk: only increases beyond the observed/billing floor are charged.
For future months the configured tariff floor supplies the baseline. Missing current-month
peak history blocks optimization; it is not zero. Internal gross peak/reserve terms and their
constant offsets are reconciled to the reported incremental objective. Terminal ESS credit
only values energy above the reserve at the frozen import tariff times discharge efficiency.
This is an opportunity-value assumption, not realized revenue. The current repository's
flat tariff profile and timestamped tariff history are retained; no live dynamic-price feed
has been invented.

Defaults allocate 30 seconds to economics and up to 30 seconds shared by refinements, with
small model-building/validation overhead. `planner.tie_break_seconds` now controls the total
refinement budget (5–120 seconds). Default relative MIP gap is 0.001. All stage objectives,
bounds/gaps, status, accepted incumbent, applied tolerance and time are archived. A skipped
stage is explicitly labelled. The fast dispatch does not wait for a solver or counterfactual.

## Configuration, safety and migration

Existing configuration groups and entity mappings remain supported. New optional fields live
in `planner`: `shadow_mode` (default **true**), `economic_tolerance_eur`,
`robustness_tolerance_kwh`, `operations_tolerance_events`, `stability_tolerance_kwh`,
`grid_import_limit_kw`, `grid_export_limit_kw`, `archive_max_mb`, and `archive_keep`.
The default 25 kW grid envelopes are configurable planning ceilings, **not inferred service
ratings**. Set them to the actual installation limits before live activation. The fast loop
reduces EV requests when measured net load exhausts import headroom. Uncontrollable household
load/PV can still exceed a grid envelope when actuator capability is exhausted; diagnostics
request replanning. The planner is not a replacement for electrical protection.

Shadow mode blocks **all actuator service writes**, including startup force-off, neutral ESS
setpoints, reset, fault fallback and shutdown. It does not pretend to stop a charger already
controlled by someone else. Live authority requires both `planner.shadow_mode: false` and the
respective existing `ess.control_enabled` / `ev.control_enabled` flag. Existing stop-and-verify
zero, phase settling/minimum interval, stale-input holds, bounded single reset and latched fault
behavior remain intact and regression-tested.

No historic Influx rows are rewritten. Accepted intervals gain an additive `plan_id` field;
existing timestamps, measurements and dashboard queries remain compatible. No V2 optimizer
is kept as an alternate path. Roll back using the prior Git revision/release and the saved
configuration, rather than switching between two running planners.

## Archive, recovery and explanations

The add-on writes `/data/planner-v3/<snapshot_id>.json`. Schema 1 / model `3.0-preview.1` uses
content-addressed immutable canonical snapshots with checksum verification. The archive includes
observations, full forecast series, tariffs/peak baseline, resource states, generated requirements,
EV generation settings, previous accepted plan and solver policy. Only the necessary whitelisted
inputs are archived: no Supervisor token, database password or unrelated configuration dump.

Each complete decision is written to a private temporary file, fsynced and atomically renamed.
Defaults retain at most 500 records and 256 MiB (whichever is reached first); a record is capped
at 32 MiB. Oldest decisions are removed on save. Retention limits refer to retained records;
an in-progress atomic write can temporarily add one record. After a crash, incomplete temporary
files are ignored and files older than a day are cleaned when opening the store. Corrupt files
produce explicit read/checksum errors, never fabricated plans. Unknown schemas/models are rejected:
use the matching release for historic replay. Existing telemetry/configuration migrations continue
unchanged; there was no pre-V3 snapshot format to convert.

Startup never restores hardware commands from disk. A new validated plan and deliberate live
opt-in are needed. An unwritable/full archive reports `persisted: false`; control can still use a
validated plan, and operators should restore storage before relying on historical explanations.
Plan IDs link HA plan diagnostics, Influx accepted intervals and the archive. Decision diffs record
known changes; they do not infer that a correlated PV change caused a particular slot.

The focused **Decision details** dashboard view provides bounded latest requirement/stage evidence.
Load an exported decision JSON to select a requirement or EV session and inspect the full data.
The session panel supplies the exact counterfactual CLI command. Load its output to inspect economic
and operating differences. Imported JSON stays in the browser and is rendered as text, not HTML.
No unauthenticated HTTP control/explanation endpoint is opened. Large snapshots are not placed in
HA sensor attributes. Existing Overview/Planning/Performance/Diagnostics views and the unavailable
monthly-peak handling are retained. Update the resource URL to
`/local/energymanager-timeline-card.js?v=300b1` and refresh the browser.

## Local review, replay and counterfactuals

```sh
cd /workspace/EnergyManager
source .venv/bin/activate
export PYTHONPATH="$PWD/energymanager/src"
ruff check energymanager/src tests tools
pytest
python tools/benchmark_v3.py
python -m energymanager.replay --archive .v3-evidence/archive list
python -m energymanager.replay --archive .v3-evidence/archive show SNAPSHOT_ID
python -m energymanager.replay --archive .v3-evidence/archive regenerate SNAPSHOT_ID
python -m energymanager.replay --archive .v3-evidence/archive replay SNAPSHOT_ID
python -m energymanager.replay --archive .v3-evidence/archive counterfactual SNAPSHOT_ID forbid_ev 0 4
```

Indexes select frozen quarter-hour slots; the end index is exclusive. `forbid_ev` postpones/excludes
charging in the selected window. `continuous_ev` requires charging in every selected slot and
rejects windows containing unavailable slots. `no_grid_import` forbids **all** grid imports in that
window: source-specific attribution of fungible AC electricity to EV is not safely identifiable.
There is no misleading "EV-only grid prohibition". Requests are limited to one intervention,
672 intervals and 60 seconds per solve (baseline plus alternative, at most two solves). Requests
never modify the live plan/archive or contact HA. Infeasibility is joint-constraint evidence;
no minimal conflicting requirement set is claimed.

The benchmark writes ignored synthetic evidence to `.v3-evidence/`, including a seven-day archived
snapshot and full counterfactual JSON. See [V3 validation](V3-validation.md) for measured results.

## Shadow-only installation, then deliberate activation

These are review instructions, not an executed deployment. Nothing has been pushed or published.

1. Review the local branch/diff and run the checks above. Save the current add-on configuration
   and the prior release reference. Arrange safe device ownership before stopping any live controller.
2. After separate deployment approval, copy `energymanager/` into a local HA add-on directory with
   a distinct slug (for example `energy_manager_v3`). In that **installation copy**, remove `image:`
   so Supervisor builds the reviewed source instead of pulling an unpublished preview image.
   Do not run two EnergyManager instances that publish the same diagnostic entities concurrently.
3. Configure the existing entity mappings, capacities/efficiencies, explicit EV minimum and weekly
   trips, tariffs and actual grid limits. Keep `planner.shadow_mode: true` and both control flags false.
   The Supervisor supplies its runtime token; do not paste one into the repository.
4. Start the shadow add-on. Verify input freshness, complete peak history, actual HiGHS validation,
   archive persistence, predicted energy balances/departures and zero actuator service writes.
   Install/update the dashboard resource and inspect/replay archived decisions and alternatives.
5. Only after review and separate live-activation approval, stop the shadow instance, ensure sole
   device ownership, and deliberately set `planner.shadow_mode: false` plus the required device control
   flags. Verify configured sensors, interlocks and limits first. Restart under supervision; startup
   neutralization then becomes an intentional hardware operation. Retain the prior release for rollback.

## Current limits

This preview has no new DHW/appliance hardware integrations and no source-specific attribution or
minimal infeasibility certificate. Robustness is heuristic; terminal value uses the existing flat tariff.
Seven-day MILPs can time out with a validated feasible incumbent and unproven lower-priority stages.
Near-equivalent schedules can still differ across timeout runs. HA browser behavior and physical
hardware operation require installation-specific validation; automated tests and synthetic replays
cannot substitute for it. Container packaging status is recorded separately in the validation report.
